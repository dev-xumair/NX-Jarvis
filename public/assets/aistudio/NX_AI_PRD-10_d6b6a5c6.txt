CORE PRODUCT RULE
-----------------
"Kaam karo, verify karo, phir bolo."

NX must never claim a task is complete merely because a tool returned success. Real state must be
verified before completion is reported.

1. PRODUCT VISION
-----------------
NX AI is a lightweight, local-first, voice-first Windows assistant for a small shop environment.
It is a professional assistant/agent, not a toy chatbot, mascot or generic ERP.

Primary jobs:
- USB detection, pack preparation, copying and verification
- File/drive management and safe cleanup
- Windows diagnostics and safe system controls
- Local voice interaction
- Online research and assisted form/application workflows
- Cover letters and other approved documents
- User-controlled memory
- Multi-provider AI reasoning and routing
- Security, recovery and diagnostics

The product must work locally for core tasks when internet or cloud AI is unavailable.

11. DRIVE / STORAGE RULE — IMPORTANT
------------------------------------
C: is the protected system drive.

Normal NX data management excludes C:.

Protected examples include:
- C:\Windows
- C:\Program Files
- C:\Program Files (x86)
- C:\ProgramData
- system32
- boot/system-critical paths
- other explicitly protected system roots

NX must not perform normal cleanup or destructive data management inside protected C: locations.

Every drive OTHER THAN C: may contain user data and may be managed under NX safety controls.
Examples:
- D:
- E:
- F:
- G:
- external HDD/SSD
- USB/removable media

D:\Downloads\NX may be an existing NX working/download/data location, but it must be configurable.
It must not be hardcoded as the universal data root.

16. ACTION RISK / CONFIRMATION POLICY
--------------------------------------
READ_ONLY:
- inspect
- search
- calculate size
- show information

These can normally execute automatically.

SAFE_REVERSIBLE:
- open application/folder
- create folder
- limited rename/move
- other explicitly reversible operations

May auto-execute when policy allows and an undo/recovery path exists.

MODERATE / BULK:
- bulk rename
- bulk move
- broad cleanup
- broad file organization

Preview and confirmation are required when thresholds are exceeded.

DESTRUCTIVE:
- delete personal files
- permanent delete
- overwrite important existing data
- format drive

Explicit confirmation is required. Prefer Recycle Bin/recoverable moves.

SECURITY-SENSITIVE:
- firewall/security state
- antivirus state
- UAC/security controls
- credentials/provider changes

These require explicit confirmation or are blocked by policy.

External actions such as sending messages, financial transactions or form submissions always require
explicit confirmation at the appropriate final step.

A confirmation must name the exact action, target and relevant counts/values. A generic "are you sure"
is not sufficient.
Only an explicit Yes/Haan/approved button counts. Silence does not count.

17. SELF-ENABLE SAFE SETTINGS
-----------------------------
When a user task depends on a SAFE and reversible setting being off, NX may:
1. identify the dependency;
2. tell the user briefly;
3. enable it;
4. perform the task;
5. verify the result;
6. optionally restore the previous setting.

NX must never silently disable firewall, antivirus, UAC or other security protections.

18. USB DETECTION
-----------------
On new USB detection NX should prompt, for example:
"Yes Boss, nayi USB lagi hai. Kya bharna hai?"

Target responsiveness: prompt within approximately 3 seconds where system conditions permit.

USB must not be written to until the task is understood and required confirmation is complete.

The system should use Windows device notifications with a short polling fallback if needed.

19. USB IDENTITY
----------------
Drive letter alone is never trusted.

USB identity should combine available signals such as:
- volume serial
- filesystem
- label
- total capacity
- vendor/product/device information
- device instance information where available
- mount information
- additional fingerprint metadata when needed

Drive letter is a mutable attribute, not the primary identity.

If identity is uncertain:
- stop
- do not guess
- ask the user

Cloned USB serials must be handled carefully. Any extra fingerprinting marker or verification must only
be created after appropriate confirmation and must not rely on unsafe hidden writes.

20. MULTI-USB TASK CONTEXT
--------------------------
Every USB has an independent task record.

Examples:
- USB A = Gaane
- USB B = Movies
- USB C = Pakistani Dramay

Command resolution may use:
- explicit drive letter
- explicit physical/device reference
- "pehli USB"
- "jo abhi lagayi"
- only pending USB

If multiple targets are ambiguous, NX must ask which one.

Copy jobs can run concurrently only within a bounded resource limit. Default concurrency can be low
(e.g. 2) and must be configurable/resource-aware.

Each write batch must re-check the physical USB identity before writing.

22. PRE-COPY VALIDATION
-----------------------
At minimum check:
1. source file count
2. file types by extension/signature where practical
3. zero-byte files
4. unreadable/inaccessible files
5. suspicious/broken media indicators where feasible
6. duplicates
7. filename/path compatibility
8. required bytes vs free space
9. FAT32 4 GB single-file limit
10. source/manifest consistency where a previous manifest exists
11. permissions
12. destination collisions
13. write-test where appropriate
14. broken-media indicators where feasible

Do not copy known-bad files silently.
The user must be told what will be skipped or what needs a decision.

23. MEDIA INSPECTION
--------------------
For video, inspect where available:
- filename
- extension
- size
- duration
- resolution
- codec
- container
- playable/readable state

For audio:
- filename
- size
- duration
- bitrate
- format
- readable state

For drama classification, use verified filename/metadata/folder context. Never invent a title or episode.
If the file name is insufficient, say the title/episode could not be identified with confidence.

24. DUPLICATE DETECTION
-----------------------
Tiered duplicate strategy:
1. filename, normalized/case-insensitive
2. name + size / size candidate filtering
3. partial hash using head/middle/tail blocks
4. full hash only where still ambiguous, high-value or explicitly requested

Large media should not be fully hashed by default when a safe cheaper method is sufficient.
Duplicates should be reported and handled according to task policy; they must not be silently deleted.

25. PRE-COPY CONFIRMATION
-------------------------
Before copying, read back as appropriate:
- target USB identity and current drive letter
- target size
- pack/source
- total file count
- total size
- free space
- duplicates
- problem files
- estimated time

Example:
"Boss, USB E:, Pakistani Dramay, 218 files, 29.2 GB. USB free 34.1 GB. 3 duplicates, 1 unreadable.
Copy start kar doon?"

Only explicit confirmation begins copying.
Formatting or deleting existing USB content is a separate action and separate confirmation.

26. TEMP COPY / ATOMIC COMPLETION
---------------------------------
Copy files to temporary .partial representations.

A file must only be renamed to its final name after the copy is considered valid and verification allows
finalization.

A partially written file must never be mistaken for a successfully completed file.

27. CHECKPOINT / RESUME
-----------------------
Store a manifest/checkpoint with relevant information such as:
- source path
- destination path
- size
- result
- hash if calculated
- batch ID
- task state
- USB identity
- progress

If USB is removed:
- stop writes
- checkpoint immediately
- mark device removed/waiting device
- notify user
- never switch to another device automatically

If the SAME physical USB returns:
- identify it
- verify state
- re-check completed files
- clean stale temporary files created by NX for that task
- ask before resume

A different USB on the same letter is a different task.

28. POST-COPY VERIFICATION
--------------------------
Verify:
- expected files exist
- sizes match
- selected hashes match
- recent/high-value files may receive full hash verification
- random sample hashing can be used
- failed files are known
- count matches expected
- manifest comparison is consistent

Honesty example:
218 source / 217 destination is NEVER "complete".
Report "partially complete" and list the missing/failed item(s).

29. RETRY / CANCEL
------------------
Use bounded retry for transient I/O failures, e.g.:
1 sec -> 2 sec -> 5 sec -> 10 sec
with jitter and a maximum retry count.

Cancel should:
- stop new writes
- checkpoint state
- clean NX temporary files only
- preserve verified user data
- avoid automatic rollback unless explicitly requested
- audit the cancellation

30. REALTIME PROGRESS

- files processed / total
- smoothed speed
- ETA
- current file
- verified count

34. NX INTERNAL STORAGE / CLEANUP
---------------------------------
Keep NX's own storage organized using separate logical areas such as:
- data/settings
- memory
- cache
- temp
- logs
- backups

Only NX-created files with a known lifecycle/ownership marker may be automatically classified as
SAFE_TO_DELETE.

Classification:
SAFE_TO_DELETE = NX-owned temporary/expired artifact
KEEP = required config/active task/recent log
USER_DATA = user-created or user-owned content
UNKNOWN = uncertain ownership

UNKNOWN and USER_DATA must never be automatically deleted.

Recommended lifecycle defaults may include:
- temporary task artifacts: short retention
- cache: age/size based eviction
- stale failed task artifacts: controlled retention
- logs: rotate by size/age
- backups: keep last N versions

Provide dry-run cleanup so the user can preview deletion.

41. GENERIC AI PROVIDER ARCHITECTURE
-------------------------------------
Gemini is the primary/default cloud AI provider for NX AI, but the agent core must remain provider-agnostic.
The provider layer is a replaceable adapter behind a stable NX internal interface.

Core rule:
- NX Agent Core never calls a Gemini SDK directly.
- The Agent Core asks the Provider Router for a model invocation.
- The Provider Router chooses a provider profile and model.
- The chosen adapter translates the normalized request to the provider API.
- The result is converted back to NX's normalized response/tool format.

The provider abstraction must support:
- provider profiles
- projects/accounts where the provider uses project-level quotas
- multiple API credentials per provider
- multiple models per credential/profile
- capability discovery
- health tracking
- rate-limit and quota tracking
- retries
- cooldowns
- failover
- task-class routing
- latency/cost awareness
- structured output/tool calling
- streaming where supported
- provider-specific grounding/search tools where supported

SUPPORTED GEMINI PROFILE CONCEPT
--------------------------------
A Gemini profile is one independently managed credential/configuration unit.

Example logical profiles:
- GEMINI_PRIMARY
- GEMINI_BACKUP_1
- GEMINI_BACKUP_2
- GEMINI_LOW_COST
- GEMINI_REASONING

A profile must store metadata such as:
- profile_id
- display_name
- provider = google_gemini
- project_identifier where applicable
- secure credential reference (never the plaintext key)
- enabled/disabled state
- user-defined priority
- preferred model role(s)
- discovered model list
- capabilities
- health state
- cooldown state
- quota/rate-limit observations
- recent latency
- recent failures by class
- last successful health check
- created/updated timestamps

CRITICAL GEMINI QUOTA RULE
---------------------------
Multiple API keys in the SAME Gemini project must NOT be treated as separate quota pools.
Google states that Gemini API rate limits are applied at the project level rather than per API key.
Therefore:

- Two keys from the same project may provide credential redundancy but do NOT multiply that project's quota.
- When one project is quota-limited, every key/profile belonging to that same project must be treated as sharing the affected quota state.
- Real quota isolation requires separate authorized projects, each with its own credential/profile and applicable quota.
- NX must never use key rotation or profile rotation as a mechanism to bypass or evade provider quotas or policy.
- Router behavior is failover and health management, not quota circumvention.

42. ADD NEW API UX
------------------
Settings -> AI / APIs -> Add New API

The UI must support adding one Gemini profile at a time and testing it before activation.

Mandatory onboarding sequence:

Step 1 — Choose provider
- User selects Google Gemini.
- Show a short explanation: "Ye NX ka online AI brain hoga."
- Do not require the user to understand developer terminology.

Step 2 — Official setup instructions
- Show only the minimum official steps needed to obtain a Gemini API key.
- Do not ask the user to paste passwords or account login credentials into NX.
- Explain that the API key is stored securely on this PC.
- If a project identifier is available, allow it to be recorded as metadata.

Step 3 — Secure credential entry
- Input must be masked.
- Key must never be shown in plain text after entry.
- Store it immediately through the OS-backed secret store or DPAPI-protected storage.
- Never put the key into normal settings JSON, SQLite plaintext columns, logs, history, crash reports, or telemetry.

Step 4 — Credential validation
- Send a minimal supported validation request.
- Distinguish authentication, permission, network, quota, model and malformed-request failures.
- Do not perform a large/expensive request just to validate a key.

Step 5 — Model discovery
- Query the provider for the models visible to the credential/project where the API supports discovery.
- Cache discovery results with a timestamp.
- Re-discover on startup when stale, after model-not-found errors, and on user request.

Step 6 — Capability discovery
For each eligible model, detect or verify where available:
- text generation
- structured output
- tool/function calling
- streaming
- vision/image input
- document/PDF input
- audio input if supported and intentionally enabled
- context size
- grounding/search support
- other provider-specific tools

Never infer support only from the model name.

Step 7 — Assign model roles
NX may recommend:
- FAST
- BALANCED
- REASONING
- VISION/DOCUMENT
- RESEARCH/GROUNDED

The user may override these assignments in Settings.

Step 8 — Health test
Run a cheap, deterministic test appropriate to the assigned role.
Record:
- success/failure
- latency
- model
- timestamp
- error class if failed

Step 9 — Save profile
Only after validation and health check pass should the profile become AVAILABLE.

Step 10 — Show human-readable result
Example:
"Gemini API add ho gayi. Connection OK, 4 compatible models mile, primary model set kar diya."

If validation fails:
"Boss, API key connect nahi hui. Masla authentication ka hai. Key dobara check karni hogi."

43. MODEL DISCOVERY / CAPABILITIES
----------------------------------
Runtime discovery is mandatory.

The implementation must not hardcode one model forever.

At PRD authoring time, Google's Gemini pricing documentation lists multiple model families, including
Gemini 2.5 Flash, Gemini 2.5 Flash-Lite, Gemini 2.5 Pro and newer Flash/Flash-Lite families. Exact model
availability, naming, access and quotas can change over time. Therefore the application must discover
what the configured project can actually use and prefer runtime capability metadata over static assumptions.

The current official pricing page indicates free access for certain models and paid tiers for higher
capacity; limits and eligible models can change. NX must expose the actual discovered availability rather
than promising a fixed free quota. [Official source: https://ai.google.dev/gemini-api/docs/pricing]

Store per-model metadata:
- model_id
- display_name
- provider
- supported input types
- supported output types
- tool calling
- structured output
- streaming
- context limit if supplied
- reasoning/thinking controls if supplied
- grounding/search capability if supplied
- availability status
- last discovery time

MODEL ROLE POLICY
-----------------
The router must select by capability and task class, not by model name alone.

Recommended logical roles:

FAST / LOW-COST
- simple classification
- short chat
- simple intent normalization
- routine extraction
- simple translation

BALANCED
- ordinary shop assistance
- normal planning
- document drafting
- moderate reasoning

REASONING
- complex planning
- code analysis
- difficult research synthesis
- multi-step ambiguity resolution

VISION/DOCUMENT
- image understanding
- scanned/visual document analysis when supported

RESEARCH/GROUNDED
- current information tasks requiring web search/grounding

A task may be promoted to a stronger model when:
- the fast model reports low confidence/insufficient capability
- structured output repeatedly fails
- the task is explicitly classified as high-reasoning
- the user requests a stronger analysis

A task must not be promoted merely because a cheap model returned a normal answer.

44. API ROUTER
--------------
The API Router is the central online AI traffic manager.

ROUTER INPUT
------------
Every online AI request enters the router with a normalized request object containing at least:
- task_id
- task_class
- user_request
- normalized context
- required capabilities
- safety/risk class
- latency target
- privacy/data-scope classification
- preferred/allowed providers if any
- preferred model role if any
- maximum retry budget
- whether web grounding is required

TASK CLASSES
------------
At minimum:
- VOICE_REALTIME
- USER_INTERACTIVE
- USB_REASONING
- FILE_CLASSIFICATION
- DOCUMENT_GENERATION
- RESEARCH
- ONLINE_APPLICATION
- DEEP_REASONING
- CODE_ANALYSIS
- BACKGROUND_ANALYSIS

ROUTING PRINCIPLE
-----------------
Use the lightest compatible model/profile that can safely complete the task.
Do not use a strong model for every request.
Do not send local-only tasks to a cloud model merely because a cloud model is available.

MANDATORY ROUTER SEQUENCE
-------------------------
1. Receive normalized request.
2. Determine whether cloud AI is actually needed.
3. If local tools can complete the request safely, keep it local.
4. If cloud AI is required, determine required capabilities.
5. Build the candidate profile set.
6. Remove disabled profiles.
7. Remove profiles in hard cooldown.
8. Remove profiles that do not support the required model capability.
9. Remove profiles blocked by policy/privacy restrictions.
10. Group candidates by Gemini project identity.
11. Apply project-level quota state.
12. Score candidates by:
   - explicit user priority
   - task compatibility
   - health
   - model capability
   - recent latency
   - cooldown proximity
   - observed quota headroom
   - cost preference where known
13. Choose the best candidate.
14. Execute request with a strict timeout.
15. Validate the response format.
16. If transient failure occurs, apply bounded retry.
17. If retry budget is exhausted, fail over to the next eligible candidate.
18. If the failure is project-level quota/rate-limit, mark the project state rather than only the individual key.
19. Re-run capability/health checks when the failure indicates stale model metadata.
20. Return a normalized result to the Agent Core.
21. Record sanitized routing/audit metrics.

MULTIPLE GEMINI PROFILE SEQUENCE
--------------------------------
The default logical sequence for a multi-profile Gemini installation is:

PROFILE 1 — GEMINI_PRIMARY
- Highest normal priority.
- Preferred for normal interactive work.
- Usually maps to a balanced/fast model role.

PROFILE 2 — GEMINI_BACKUP_1
- Separate authorized Gemini project recommended.
- Used when Primary is unhealthy, rate-limited, timed out or otherwise unavailable.
- Must not be treated as an independent quota pool if it belongs to the same project as Primary.

PROFILE 3 — GEMINI_REASONING
- Separate authorized project recommended for higher-complexity tasks.
- Preferred for DEEP_REASONING, CODE_ANALYSIS or difficult planning when the discovered model supports it.

PROFILE 4 — GEMINI_LOW_COST / EMERGENCY
- Optional.
- Used for simple requests when the stronger profiles are expensive, busy or unavailable.
- May use a current Flash-Lite class model when discovered and eligible.

The user does not have to create all profiles. The router must work with 1, 2, 3 or more profiles.
The more profiles configured, the more important clear project identity and quota grouping become.

45. API KEY / SECRET SECURITY
-----------------------------
Store API keys using Windows DPAPI, Windows Credential Manager, or an equivalent OS-backed secure store.

Rules:
- Never store plaintext keys in source code.
- Never commit keys to Git.
- Never put keys in normal JSON/YAML configuration.
- Never put keys in task history.
- Never put keys in memory.
- Never put keys in audit records.
- Never put keys in crash reports.
- Never expose keys in UI diagnostics.
- Never speak keys through TTS.
- Never include keys in model prompts.
- Never send a key to Gemini as user data.

The database may store only a secure credential reference, fingerprint/last4 if useful for UX, and metadata.

When the user edits or removes a profile:
- revoke/forget the secure reference in NX
- retain only non-secret audit metadata
- remove model/cache associations that contain the secret reference

For a single-user local desktop build, direct API calls from the installed app are allowed only through the
secure credential layer. If NX is later converted into a multi-user/distributed product, use a server-side
secret broker rather than distributing a shared master key to clients.

- PERMISSION_DENIED
- INVALID_REQUEST
- RATE_LIMITED
- PROJECT_QUOTA_EXCEEDED
- DAILY_QUOTA_EXCEEDED
- TIMEOUT
- NETWORK_ERROR
- SERVICE_UNAVAILABLE_503
- SERVER_5XX
- MODEL_UNAVAILABLE
- CAPABILITY_MISMATCH
- SAFETY_REFUSAL
- CONTENT_POLICY_BLOCK
- CONFIGURATION_ERROR
- UNKNOWN_TRANSIENT

ERROR OWNERSHIP RULE
--------------------
Each error must be assigned to the correct scope:

Credential-level:
- invalid key
- revoked key
- credential permission failure

Profile-level:
- profile misconfiguration
- unsupported model assignment
- repeated model-specific failures

Project-level:
- rate limit
- quota exceeded
- project-level service restriction

Provider-level:
- broad network/provider outage affecting all profiles

Task/content-level:
- invalid request
- schema mismatch caused by the request
- safety refusal
- user-data validation problem

Do not label every HTTP 429 as a bad API key.
Do not label every 5xx as user error.
Do not retry a permanently invalid credential forever.

47. RETRY / FAILOVER POLICY
---------------------------
GENERAL RETRY
-------------
Transient errors use bounded exponential backoff with jitter.
Reference progression:
- 1 second
- 2 seconds
- 5 seconds
- 10 seconds

Actual delay should respect provider-provided retry information where available.

SAME-PROFILE RETRIES
--------------------
Default maximum:
- 2 retries for a transient request failure on the same profile.

After the limit, fail over without waiting if another compatible profile is available.

AUTH / INVALID KEY
------------------
- No retry loop.
- Mark the credential/profile DISABLED_NEEDS_FIX.
- Keep the remaining profiles available.
- Ask the user to repair the specific profile only if needed.

INVALID REQUEST
---------------
- No automatic retry with identical payload.
- Validate the structured request.
- If fixable by the NX planner/tool schema, correct once and retry.
- Otherwise stop and report a clear error.

RATE LIMIT
----------
When the response includes retry/reset information:
- respect it
- mark the affected project/profile COOLING_DOWN
- fail over if another eligible project is available

If multiple Gemini profiles share the same project:
- propagate the affected quota state to all sibling profiles in that project
- do not repeatedly send the same failing request through each sibling key

PROJECT DAILY QUOTA
-------------------
- Mark the project as quota-exhausted until the provider indicates reset or a health test proves recovery.
- Prefer another authorized project.
- Do not create fake new identities automatically to bypass the limit.

503 / 5XX
---------
- Bounded retry.
- Then cooldown.
- Then fail over to another healthy project/model.

TIMEOUT
-------
- One bounded retry may be attempted depending on task class.
- Do not penalize a healthy profile heavily for one timeout.
- Repeated timeouts reduce health score.

MODEL UNAVAILABLE / 404
-----------------------
- Refresh model discovery.
- Verify the model still exists and is accessible.
- Select a compatible fallback model.
- Retry only after capability validation.

SAFETY REFUSAL
--------------
- Do not loop through models trying to bypass the refusal.
- Preserve provider safety behavior.
- Ask the user for a safe alternative or report that the request cannot be completed.

NETWORK FAILURE
---------------
- Do not permanently penalize the profile.
- Use local/offline features where possible.
- When network returns, perform a health check before normal online routing resumes.

ALL ONLINE PROFILES FAIL
------------------------
- Keep NX running.
- Fall back to local capabilities for tasks that support them.
- Explain truthfully which capability is unavailable.
- Do not claim the cloud operation succeeded.

48. PROVIDER HEALTH STATES
---------------------------
Per-profile states:
- NEW
- CHECKING
- HEALTHY
- DEGRADED
- COOLING_DOWN
- QUOTA_BLOCKED
- DISABLED_NEEDS_FIX
- UNAVAILABLE

Per-project states:
- UNKNOWN
- HEALTHY
- RATE_LIMITED
- QUOTA_BLOCKED
- SERVICE_DEGRADED
- UNAVAILABLE

Track:
- last success
- last failure
- error class
- model
- latency
- cooldown_until
- retry count
- rolling error count
- request count
- observed response headers/usage signals where available
- last model discovery time
- last health check

HEALTH RECOVERY SEQUENCE
------------------------
1. Cooldown expires.
2. Router sends one cheap health check.
3. If success, project/profile returns to HEALTHY.
4. If failure, extend cooldown according to error class.
5. If repeated failures exceed threshold, move to DEGRADED or DISABLED_NEEDS_FIX.
6. Never blacklist a provider forever because of a temporary outage.

49. GEMINI MULTI-PROFILE SETUP / FAILOVER SEQUENCES
----------------------------------------------------
This section is the implementation sequence Windsurf/Cascade must follow when building the multi-Gemini
system.

SEQUENCE A — FIRST PROFILE
--------------------------
1. Install NX.
2. Open Settings -> AI / APIs.
3. Choose Add New API.
4. Select Google Gemini.
5. Enter first API key securely.
6. Validate key.
7. Discover models.
8. Detect capabilities.
9. Select a safe fast/balanced default.
10. Run health check.
11. Mark profile HEALTHY.
12. Set profile as GEMINI_PRIMARY.
13. Run one end-to-end test through the real router.
14. Save sanitized audit event.

SEQUENCE B — SECOND PROFILE / BACKUP
------------------------------------
1. Add another Gemini profile.
2. Record its project identity if available.
3. Securely store its credential.
4. Validate.
5. Discover models.
6. Detect capabilities.
7. Run health check.
8. Compare its project identity with Primary.
9. If SAME project:
   - label it "Credential Backup / Same Project";
   - do not count it as independent quota capacity;
   - keep shared project quota state.
10. If DIFFERENT authorized project:
   - label it "Independent Project Backup";
   - maintain separate quota/health state.
11. Run a real failover test with a safe non-destructive prompt.

SEQUENCE C — THIRD / REASONING PROFILE
--------------------------------------
1. Add another Gemini profile.
2. Discover reasoning-capable models available to that project.
3. Assign role REASONING only after capability verification.
4. Set task classes such as DEEP_REASONING and CODE_ANALYSIS to prefer it.
5. Keep normal short shop commands on the cheaper/faster profile.
6. Test timeout, failure and fallback behavior.

SEQUENCE D — REQUEST ROUTING
----------------------------
For every request:
1. classify task
2. check local-only completion
3. if cloud required, resolve capability needs
4. build eligible profiles
5. group by project
6. apply project-level cooldown/quota state
7. choose best profile/model
8. send request
9. validate response/schema
10. execute any approved tool call through NX tools
11. verify real-world result
12. generate short user response
13. update health/usage metrics

SEQUENCE E — PRIMARY FAILOVER
-----------------------------
Example:
- Primary returns timeout.
- Retry once according to task class.
- Second failure.
- Primary enters DEGRADED.
- Router selects Backup Project.
- Backup request succeeds.
- NX completes the user task.
- User normally hears only the truthful result, not internal routing noise.
- Statistics & History records the switch.

SEQUENCE F — PROJECT QUOTA FAILOVER
-----------------------------------
Example:
- Primary Project returns rate limit/quota error.
- Router marks the PROJECT quota state.
- Any sibling keys from that same project are excluded for the affected request class.
- Router selects a healthy profile from a DIFFERENT authorized project.
- If no independent project exists, fall back to local mode where possible or tell the user online AI is
  temporarily unavailable.

SEQUENCE G — MODEL FAILOVER
---------------------------
Example:
- Selected model becomes unavailable.
- Router refreshes model discovery.
- It checks compatible models in the same profile.
- If a compatible fallback exists, use it.
- If not, fail over to the next compatible profile/project.

SEQUENCE H — RECOVERY AFTER COOLDOWN
------------------------------------
1. Cooldown expires.
2. Send cheap health check.
3. Confirm project/model still available.
4. Clear temporary error counters only after success.
5. Return profile/project to HEALTHY.
6. Restore normal priority.

FAILOVER MUST NEVER BREAK TASK SAFETY
-------------------------------------
Changing AI profile/model must not:
- skip confirmation
- skip tool validation
- change the target USB
- change the source folder silently
- bypass security policy
- bypass browser stop conditions
- bypass CAPTCHA/OTP/payment rules
- turn a refused request into an allowed one

The provider only reasons/plans. NX's policy/tool layer remains authoritative.

- active task files are protected while needed
- completed task temp artifacts may be cleaned under policy
- user data outside NX-owned temporary locations is never assumed disposable
- UNKNOWN is protected
