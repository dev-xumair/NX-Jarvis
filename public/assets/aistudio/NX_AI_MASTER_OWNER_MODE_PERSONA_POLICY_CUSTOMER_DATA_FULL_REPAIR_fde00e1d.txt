NX AI — MASTER OWNER-MODE BEHAVIOR, POLICY, DATA, PERSONA, ALIAS, TOOL-EXECUTION & FULL SYSTEM REPAIR PROMPT
===============================================================================================

PURPOSE
-------
Use this document as the authoritative implementation/repair specification for NX AI.

The current project is behaving like a capable chatbot with some verified backend modules,
but natural-language requests are not consistently reaching the actual workstation tools.
The goal of this repair is to turn NX AI into a genuine Windows desktop operator agent.

The implementation MUST:
1. Preserve the security boundary around destructive system actions.
2. Stop incorrectly blocking harmless/legitimate owner operations.
3. Allow owner-configured secure handling of customer records and sensitive business data.
4. Keep passwords, OTPs, API keys and similar secrets out of logs, chat history and normal memory.
5. Add a configurable female persona, multiple aliases, wake names and behavior profiles.
6. Make aliases/behavior profiles fully editable by the owner.
7. Connect natural-language intent to real registered tools/workers.
8. Actually execute, observe and verify tasks instead of only describing scripts.
9. Distinguish clearly between:
   - feature exists but host is unavailable
   - feature exists but not configured
   - feature exists and is ready
   - feature was actually executed and verified
   - feature is blocked by policy
10. Never fake a successful action.

IMPORTANT IMPLEMENTATION RULE
-----------------------------
Do not rewrite the whole project blindly.

First inspect the existing repository, current architecture, current route names, workers,
providers, persistence layer, UI, tests, policy engine, and current verification ledger.

Then:
A. preserve working pieces,
B. repair broken connections,
C. remove obsolete/conflicting implementations,
D. add missing adapters,
E. run tests,
F. perform live verification on supported host(s),
G. update the verification ledger truthfully.

PART 2 — POLICY ENGINE REWORK
================================================================================

CURRENT PROBLEM
---------------
The current policy behavior is overblocking.

Examples from testing:
- harmless chained command input was interpreted as injection and halted too broadly
- a large multi-task capability test was blocked because sensitive terms occurred in the request
- file/media/browser tasks were reported as unavailable even though backend capabilities are
  claimed elsewhere

REBUILD THE POLICY ENGINE AROUND ACTION RISK, NOT KEYWORD PRESENCE ALONE.

Create risk classes:

R0 — INFORMATIONAL
Examples:
- "Hi"
- "What's your name?"
- "What can you do?"
- system capability list
- skill list
- provider list
- model status
- task planning
- explaining a command

Normally allowed.

R1 — READ-ONLY LOCAL ACTION
Examples:
- inspect RAM
- inspect CPU
- list folders
- search files
- list USB devices
- inspect browser installation
- inspect Android devices
- inspect storage
- inspect logs that the owner is allowed to read

Normally allowed without extra confirmation.

R2 — REVERSIBLE WRITE ACTION
Examples:
- create a temporary file
- rename a file
- copy a file
- create a folder
- write a generated document
- organize a folder using a reversible operation

Allow based on owner preferences.
For meaningful batch operations, show a concise action summary before execution unless the
owner has explicitly enabled autonomous mode for that category.

R3 — EXTERNAL / ACCOUNT / COMMUNICATION ACTION
Examples:
- send a message
- publish content
- upload a file
- send email
- modify an online account
- submit a form
- perform a purchase

Require confirmation by default.
Owner may configure trusted apps/workflows where appropriate.

R4 — SENSITIVE DATA OPERATION
Examples:
- create/read/update customer records
- store CNIC number
- store phone number
- store address
- store account references
- process an API key
- use a password in an authenticated action
- receive an OTP

Do NOT block merely because sensitive data is present.

Instead:
- process only for the requested purpose
- use encrypted storage where persistence is required
- redact from standard logs
- never place secrets in normal chat history
- never expose secret values in diagnostics
- apply field-level access rules
- audit the action without recording secret contents.

R5 — DESTRUCTIVE / HIGH IMPACT
Examples:
- format C:
- delete OS/system directories
- wipe a drive
- destructive disk partition operations
- irreversible mass deletion
- disable critical security controls
- unauthorized credential extraction

Always block or require explicit high-risk confirmation according to the final policy.
C: / Windows system volume must remain protected.

IMPORTANT:
Do NOT treat these as the same:
"search for CNIC"
"save customer CNIC in secure database"
"show me a customer's CNIC"
"send CNIC externally"
"dump all CNICs to a text file"

Each needs its own risk decision.

Never use:
"Sensitive credentials detected, request halted"
as a generic response to a legitimate, owner-authorized customer-record operation.

Instead, route the request to the correct secure-data worker.

SECURITY MODEL
--------------
Use encrypted persistent storage.

- field-level encryption for sensitive values
- encrypted local key vault
- OS-level file permissions where available
- secure key derivation
- rotating encryption key support
- backup/export with explicit user action

- do not put full CNIC in application logs
- do not display full CNIC everywhere
- default UI should mask it, e.g. *****1234
- allow authorized reveal only inside the customer record view
- never expose it in diagnostics/test telemetry

PASSWORDS / OTP / API KEYS:
- do NOT place these into customer normal records
- do NOT put these into chat memory
- do NOT print them in the console
- do NOT put them into verification snapshots
- use a secure credentials vault instead
- show only masked references such as VAULT:XXXX...XXXX
- allow the owner to use the credential for a task without revealing the underlying secret

PART 20 — MULTI-TASK MESSAGE HANDLING
================================================================================

The long capability test previously triggered a false sensitive-data halt.

FIX THIS.

When a message contains 20 tasks:
1. parse each task into subtask records
2. classify each independently
3. execute allowed tasks
4. request confirmation only for tasks that need it
5. skip unavailable tasks with exact reason
6. continue with safe tasks
7. summarize all results

Do NOT halt the entire request merely because one subtask contains:
- password
- API key
- CNIC
- OTP
unless the actual requested operation is unsafe or unauthorized.

Example:
A request containing:
"Do not show API keys in plaintext"
must NOT be treated as an attempt to access an API key.

The intent classifier must understand NEGATION and CONTEXT.
