2. NEW DRIVE SOURCE-OF-TRUTH RULE
======================================================================

OLD D-DRIVE-ONLY ASSUMPTION AB VALID NAHI HAI.

C: drive SAFE / PROTECTED SYSTEM DRIVE hai.
C ke ilawa har available data drive NX AI ke data-operation scope mein aa sakti hai: D:, E:, F:, G:, external HDD, USB aur other mounted storage.

LEKIN non-C ka matlab free-for-all deletion nahi hai.

C drive:
- default protected
- Windows/system folders ko touch/delete/modify nahi karna
- Program Files, ProgramData, Users ke critical paths aur boot/system areas protected
- destructive C-drive operations BLOCKED by default
- legitimate system settings dedicated safe tools se perform ho sakti hain

Non-C drives:
- scan
- organize
- duplicate detection
- cleanup
- quarantine
- copy/move
- catalog/index
- watcher
- user-authorized delete

Destructive flow:
SCAN -> PLAN -> PREVIEW -> CONFIRM -> BACKUP/RECOVERY PLAN -> EXECUTE -> VERIFY

D:\Downloads\NX agar existing NX download/data location hai to isko default cleanup se protect karo. Ye path configurable hona chahiye; hardcode permanent assumption mat banao. Config values jaise NX_DATA_ROOT, NX_DOWNLOAD_ROOT, NX_TEMP_ROOT use karo.

4. CORE ARCHITECTURE
======================================================================

Recommended modular architecture:

NX Core
 + Voice Layer: wake, VAD, STT, session, TTS, barge-in

Use modular boundaries. Giant main.py/god class avoid karo.

======================================================================
20. C DRIVE PROTECTION
======================================================================

Default protected paths include:
C:\Windows
C:\Program Files
C:\Program Files (x86)
C:\ProgramData
critical boot/system paths
system32
registry/system-critical areas

No format C:, destructive disk/boot operations, mass destructive commands.

Legitimate system settings should use dedicated Windows APIs/tools, not arbitrary shell.

======================================================================
21. NON-C DRIVE MANAGEMENT
======================================================================

D/E/F/G/etc can be managed under safety policy.

Read-only tasks can often auto-run.
Destructive operations use:
PLAN -> PREVIEW -> CONFIRM -> EXECUTE -> VERIFY

Never assume all non-C files are disposable.

======================================================================
22. USB DETECTION + IDENTITY
======================================================================

USB insertion:
"Yes boss, new USB lagi hai. Kya bharna hai?"

Each USB has independent task context.

Do not depend only on drive letter.

Identity combine:
- volume serial
- device information
- filesystem
- capacity
- mount info
- fingerprint metadata
- other stable identifiers where available

Clone USBs may share serial. Fingerprint/content metadata must provide additional disambiguation. If identity uncertain, stop and ask.

No automatic execution from USB.

======================================================================
23. USB COPY ENGINE
======================================================================

Transactional flow:
SOURCE SCAN -> PRE-COPY VALIDATION -> SPACE CHECK -> DESTINATION VALIDATION -> PLAN -> CONFIRM -> TEMP COPY -> BATCH IDENTITY CHECK -> WRITE -> CHECKPOINT -> VERIFY -> ATOMIC RENAME -> FINAL VERIFY -> REPORT

Write large files to temporary names such as filename.partial. Only verified successful copies get final names.

Before each batch:
- USB identity
- destination mounted
- filesystem
- free space
- source accessibility

If USB changes/removes:
STOP, checkpoint, notify. Never automatically continue on a different device.

======================================================================
24. PRE-COPY VALIDATION
======================================================================

At minimum:
1 File count
2 Zero-byte files
3 Unreadable files
4 Duplicate candidates
5 Free space
6 FAT32 4GB limitation
7 Filename/path problems
8 Manifest
9 Source consistency

Also check suspicious extensions, permissions, destination collisions, write test, broken media where feasible.

======================================================================
25. DUPLICATE + VERIFICATION
======================================================================

Duplicate levels:
1 name
2 name + size
3 head/middle/tail partial hash
4 full hash only when necessary

Post-copy verification:
- existence
- size
- recent/high-value full hash
- random sample hash
- failed-file verification
- count/manifest comparison

218 source, 217 destination = NEVER say complete. Report partial and failed filename(s).

======================================================================
26. RETRY / CANCEL / PROGRESS
======================================================================

Bounded retry with exponential backoff + jitter, e.g. 1s, 2s, 5s, 10s, configurable.

Permanent errors should not retry endlessly.

Cancel:
- stop new writes
- safely abort active work
- checkpoint
- clean NX temp files only
- preserve verified user data unless explicit rollback
- audit

Real progress:
bytes completed/total
files completed/total
smoothed speed
ETA
current file
failed count

No fake progress.

======================================================================
27. VOICE PIPELINE
======================================================================

Wake Detection -> VAD -> Local STT -> Intent -> Context -> Planner -> Tool -> Verification -> Response -> Local TTS

Wake audio must NOT be sent to Gemini.

Wake aliases:
NX, Nazim Assistant, NX Assistant, Hey AI, Handsome, Smart, Bro

Two-stage wake:
Stage 1 cheap local keyword detector
Stage 2 local STT/context confirmation

False wake example "Ye smart phone hai" must not activate reliably just because word Smart appears. Use confidence, phrase boundary and context.

======================================================================
28. STT/TTS/BARGE-IN
======================================================================

Benchmark local STT candidates such as Whisper Tiny/small local variants and Vosk on actual target hardware for RAM, CPU, speed, Urdu/Roman Urdu accuracy and noise robustness. Do not choose by internet opinion alone.

4GB Light Mode should use the lightest acceptable model/settings.

Low confidence:
DO NOT execute. Ask clarification.

Drive/pack/digits/name and other critical values should be read back and confirmed.
Silence is NOT consent.

TTS should be local/offline-capable. Evaluate Piper vs pyttsx3 for quality, latency, RAM and Roman Urdu behavior. Tune normalization for Roman Urdu, numbers and abbreviations.

Barge-in: when user speaks, stop TTS quickly (target perceived response around 300ms where hardware permits) and preserve context.

Noise handling:
- noise suppression
- VAD
- gain tuning
- echo cancellation where available
- optional push-to-talk
- clarification on ambiguity

Do not pretend perfect speaker separation on a single inexpensive mic.

29. ONLINE APPLY AGENT
======================================================================

Example "Apna Ghar Apni Chhat apply karna hai" must NOT jump directly to submit.

Website changes:

======================================================================
30. FORM DATA SAFETY
======================================================================

Required document missing = block submission.
Optional missing = continue only if official form allows.

NEVER invent:
CNIC, phone, DOB, address, bank/card, OTP, application number, education, employment, legal facts.

OCR uncertain -> human confirmation.

Before submit, read back all important fields and ask clear confirmation.
Silence = no submit.

CAPTCHA, OTP, payment confirmation, biometric, PIN, password and identity challenge = STOP and hand control to user. Do not bypass.

======================================================================
33. DRIVE MANAGEMENT / MEDIA / JUNK / VIRUS
======================================================================

Before management:
SCAN -> CLASSIFY -> PLAN -> PREVIEW -> CONFIRM -> BACKUP/RECOVERY -> EXECUTE -> VERIFY -> REPORT

Do not repeatedly full-scan 500GB. Use metadata index, timestamps, cached hashes, filesystem watcher and incremental reconciliation.

Drama/media classifier:
filename + extension + size + duration + resolution + codec/container + folder context + episode/season pattern + metadata.
Do not claim content was listened/watched if it was not.

Duplicate episodes compare resolution, bitrate, codec, size, duration, readability. Do not auto-delete lower-quality candidate.

Junk candidates:
temp, incomplete downloads, zero-byte, obvious temp duplicates, stale cache/installer fragments. Unknown/user/business files remain protected.

Virus detection:
Windows Defender/available AV + hash/reputation where safe + suspicious metadata/behavior. Suspected malware -> QUARANTINE, not immediate deletion. Never disable antivirus.

Prefer Recycle Bin/recoverable move. Permanent delete requires explicit confirmation.

======================================================================
34. AUTO ORGANIZE + CATALOG
======================================================================

New file watcher must wait until writing/copying is finished, then classify, duplicate-check, target folder, move under configured policy, update catalog, verify.

Catalog:
title, season, episode, quality, size, duration, path, hash reference, status, detected_at, last_seen.

Missing file -> mark missing; reconcile before removing stale records.

36. MEMORY + AUDIT
======================================================================

Memory and audit are separate.

Memory = useful facts/preferences/tasks.
Audit = what action happened.

Audit fields:
timestamp, task_id, tool, action, risk, actor, result, error, confirmation, affected resource/path, hash where relevant.
Never store secrets.

======================================================================
37. PERFORMANCE / LIGHT MODE
======================================================================

Target hardware: 8GB RAM Windows PC.
Goal: low idle RAM, fast startup, non-blocking UI, lazy loading, async I/O, bounded workers, streaming, resource-aware voice.

Target idle RAM under approximately 500MB where technically realistic. Measure it; never fake it.

4GB Light Mode:
- reduce/disable continuous deep indexing
- reduce media analysis
- avoid large local models
- reduce animations
- pause background deep scans
- reduce concurrency
- reduce caches
- keep core voice/STT, agent, USB, file ops, safety, memory and essential UI

Resource manager tracks CPU/RAM/disk and reduces optional background load under pressure.

Queues:
VOICE_REALTIME
USER_INTERACTIVE
CRITICAL_TASK
BACKGROUND_TASK
INDEXING

Large copy must not block voice. CPU-heavy STT/media processing may need process isolation.

======================================================================
38. STARTUP / LAZY LOADING / LOGS / ATOMIC STATE
======================================================================

Startup loads only:
core config, DB, security, UI, lightweight voice readiness.

Lazy-load:
browser, media analyzer, document engine, heavy STT, indexer, advanced diagnostics.

Structured logging levels DEBUG/INFO/WARNING/ERROR/CRITICAL.
Rotate logs; e.g. bounded 10MB files with 5-10 backups or equivalent. No 1GB log.
Never log secrets.

Critical state:
write temp -> flush -> atomic replace. SQLite transactions for DB state.

======================================================================
39. TASK SCHEDULER + CRASH RECOVERY
======================================================================

Task fields:
id, type, priority, state, created, started, updated, checkpoint, resource class, dependencies, parent, result, error.

States:
QUEUED, RUNNING, PAUSED, WAITING_USER, WAITING_DEVICE, WAITING_NETWORK, FAILED, RECOVERING, COMPLETED, CANCELLED

Priority:
1 active user interaction
2 safety/security
3 user-confirmed critical task
4 normal interactive
5 background

Avoid deadlock through timeouts, lock ordering, cancellation and no nested blocking locks.

On startup inspect incomplete tasks. Auto-resume only safe tasks after validating checkpoint/device/resource state. Dangerous/uncertain tasks require user.

======================================================================
40. FILE INDEXING
======================================================================

Index configured non-C data drives. Initial scan + incremental watcher + periodic reconciliation.
Exclude NX internal temp, protected/system folders and configured exclusions.
Do not crawl everything at maximum speed forever.

======================================================================
41. WINDOWS DIAGNOSTICS
======================================================================

"NX apna checkup karo" should check:
runtime, dependencies, DB, permissions, mic, speaker, STT, TTS, API health, disk, RAM, CPU, browser, filesystem, logs, security.

Output PASS/WARNING/FAIL with safe remediation.

Explain likely causes of high RAM/CPU, slow startup, app hang, network/USB/audio/STT/API problems. Never blindly kill processes.

======================================================================
42. SECURITY HARDENING
======================================================================

Rank vulnerabilities CRITICAL/HIGH/MEDIUM/LOW.

Defenses:
- allow-listed tools
- path sandboxing
- secret protection
- safe subprocess
- no arbitrary shell
- no model-generated raw command
- least privilege
- confirmations
- audit
- AV integration
- file validation
- browser domain/file permissions
- timeouts
- dependency pinning

Path validation:
normalize/resolve paths, compare against explicit allowed roots, reject traversal, dangerous UNC/device paths and sandbox escapes where relevant.

USB:
no autorun/no automatic execution. Treat .exe .bat .cmd .ps1 .vbs .js .scr .lnk as potentially dangerous and apply security policy.

Browser automation must not upload arbitrary local files. Only files explicitly required and authorized.

======================================================================
43. BACKUP / ROLES

Optional encrypted local/external/cloud backup. Never silently upload user data. Recovery tests should exist.

If multi-user access is implemented:
Admin and Staff roles. Admin controls APIs/security/settings/destructive actions. Staff limited. Do not overbuild if one-user deployment is enough; keep architecture extensible.
